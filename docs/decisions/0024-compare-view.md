# 0024 구성 비교 화면: 통합 트리와 나란히 두 트리를 비교 띠에서 전환

- 상태: 확정 (사용자 선택, 디자인 세션 시안, 기능 세션 공수 검토)
- 날짜: 2026-10-03

## 맥락
W19는 같은 Board의 두 구성(과거 대 현재, 또는 임의의 두 revision)을 비교해 W16 차이 결과를 보여 준다. PRD §6-E는 변화 종류를 구분하고
변화 없음을 명확한 빈 상태로 보이도록 정했다. 기능 세션의 제약: 이력 목록은 단일 선택을 유지하고, 고른 두 revision만 디코딩하며,
Node 500개 규모에서 지연 목록이면 충분하다.

## 결정
디자인 세션이 실제 SwiftUI 컨트롤로 세 구조를 렌더링했다. A는 변경 목록, B는 나란히 두 트리, C는 통합 트리다. 사용자는 B와 C를
둘 다 두고 고를 수 있게 하자고 했다. 개발자에게는 B가, 그 밖의 사용자에게는 B나 C가 익숙하다는 이유다.
- 비교 띠 안의 '통합 | 나란히' 세그먼트로 바꾼다. 마지막 선택을 기억하고, 기본값은 통합이다(설정 창에는 두지 않는다).
- 통합 트리: 이후 구성 트리에 변화 표시를 붙이고, 제거된 항목은 이전 위치에 '제거됨' 행으로 끼워 넣는다. '바뀐 항목만 보기' 거르기를 둔다.
- 나란히 두 트리: 이전과 이후 트리를 두고, 고른 항목을 양쪽에서 함께 강조하며 고른 행으로 스크롤한다.
- 진입점: 과거 구성 띠의 '현재와 비교'(기본), 이력 행 오른쪽 클릭 '이 기록과 비교', 비교 띠의 대상 메뉴. 이력 목록은 단일 선택을 유지한다.
- 비교는 목록 형태로만 보여 준다. 아이콘 보기에서 비교를 열면 그 비교 동안 목록 형태로 보인다.
- 변화 종류는 기호와 문구로 표시하고(DESIGN.md 19.3), 색만으로 구분하지 않는다. '순서 변경 표시' 거르기를 둔다.

## 대안
- C만: 구현이 가장 작지만, 개발자 사용자에게 익숙한 나란히 비교가 없다.
- B만: 가운데 영역을 둘로 나눠 트리가 좁아지고, 이동한 항목을 눈으로 잇기 어렵다.
- A 변경 목록: 훑어보기는 좋지만 트리 안의 위치를 문구로만 알 수 있다.
- 설정 창에서 방식 고르기: 비교하면서 두 방식을 오가기 어렵다.
- 이력 목록을 다중 선택으로 바꿔 두 revision 고르기: W17·W18의 단일 선택 구조(고른 행 = 과거 구성)를 깨뜨린다.

## 영향
- 공수(기능 세션 추정): 나란히 두 트리를 더하는 비용은 통합 트리만 만들 때보다 약 25–35% 더 든다. 더 무거운 쪽은 통합 트리의
  '제거됨' 끼워 넣기 규칙(Domain 결정표)이다.
- 구현은 W19 명세 게이트 하나로 두 방식을 함께 통과시키고, PR 두 개로 나눈다: ① 공통 부분 + 통합 트리, ② 나란히 + 세그먼트.
  작업 항목을 따로 쪼갤지는 사용자가 정한다.
- 이력 탭 revision 행에 오른쪽 클릭 '이 기록과 비교'가 더해진다(16장).
