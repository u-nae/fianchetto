# Fianchetto PRD

버전: 1.0
작성일: 2026-09-30 (Asia/Seoul)
상태: 구현 인계 기준. 앱 구현 및 성능 검증 전.
대상: macOS 개인용 첫 버전
관련 문서: [기술스택 결정서](./TECH_STACK.md)

## 1. 제품 정의

Fianchetto는 실제 파일을 이동하지 않고, 흩어진 로컬 파일·폴더를 논리적인 프로젝트로 연결하는 macOS 앱이다. 사용자가 만든 이름과 구조를 유지하면서 실제 연결 대상을 교체할 수 있고, 구성 변화와 작업 체크포인트를 기록해 과거 작업 맥락으로 돌아갈 수 있다.

제품의 약속: **프로젝트에 어떤 자료가 연결되어 있었고, 그때 어디까지 작업했는지 기억한다.**

이름은 우선 Fianchetto를 사용한다. 비숍의 명확한 이동 범위와 긴 대각선 연결을 모티프로 삼는다. 사용자가 지정한 범위에서 빠르고 신뢰할 수 있게 동작하는 도구를 지향한다. 브랜드 모티프가 사용자에게 체스 규칙 학습을 요구해서는 안 된다. UI 용어는 프로젝트·그룹·연결·이력·체크포인트를 사용한다. 이름은 추후 변경 가능하며 데이터 형식을 이름에 과도하게 결합하지 않는다.

## 2. 해결할 문제와 사용자

### 문제

개발 중에는 소스 저장소, 문서, 디자인 에셋, 참고 파일이 여러 디렉토리에 흩어져 있다. 물리적인 폴더 구조만으로 여러 논리적 작업 단위를 동시에 표현하기 어렵다. 시간이 지나면 참조 자료와 저장소가 바뀌고, 현재의 바로가기 목록만으로 한 달 전 구성이나 작업을 중단한 지점을 재구성하기 어렵다.

### 첫 사용자

제품을 구상한 사용자 본인. macOS에서 여러 코드 저장소와 자료 폴더를 다루며, 사용 빈도가 높지 않아도 중단한 프로젝트를 다시 시작할 때 확실히 도움이 되는 가벼운 도구를 원한다.

후속 사용자 가설은 다중 저장소 개발자, 프리랜서, 연구자, 디자이너다. 외부 유료 수요는 아직 검증하지 않았다. 대중적인 사용량·시장 규모를 가정해 기능을 확장하지 않는다.

### 대표 시나리오

1. 사용자가 `서비스 A` 프로젝트를 만든다.
2. `개발` 가상 그룹 안에 `backend` 연결 폴더를 만들고 `/dev/legacy-api`에 연결한다.
3. 문서와 에셋 폴더, API 명세 웹 링크를 함께 배치한다.
4. 리팩토링 후 `backend`의 대상만 `/dev/new-api`로 바꾼다.
5. 앱에는 같은 `backend` 항목이 유지되고, 대상 교체가 이력에 남는다.
6. `인증 리팩토링 1차 완료` 체크포인트에 진행 메모와 다음 할 일을 남긴다.
7. 한 달 뒤 과거 날짜를 선택해 당시 구성과 체크포인트를 확인한다.
8. 과거 연결을 열거나, 현재와 차이를 비교하거나, 그 구성에서 새 프로젝트를 만든다.

## 3. 목표와 첫 버전의 완료 정의

### 목표

- 실제 파일의 위치와 별개인 논리적 자료 구성을 제공한다.
- 연결 대상 교체 후에도 항목의 논리적 정체성과 이력을 유지한다.
- 구성 변화 기록을 사용자에게 매번 요구하지 않는다.
- 의미 있는 시점에만 이름과 작업 메모를 남길 수 있다.
- 과거 구성 조회와 복원 과정에서 현재 자료와 과거 자료를 혼동하지 않게 한다.
- 로컬에서 독립적으로 동작하고, 유휴 상태에 불필요한 작업을 하지 않는다.

### 완료 정의

실제 사용자가 프로젝트 생성 → 파일·폴더 연결 → 대상 교체 → 앱 재실행 → 과거 구성 조회 → 비교 → 체크포인트 확인 → 복원 또는 복제 → 내보내기·가져오기를 수행할 수 있다. 원본 파일 내용이나 위치는 앱의 구성 작업으로 바뀌지 않는다. 필수 수용 기준과 핵심 데이터 불변식이 검증되어야 한다.

### 후속 검토

연결 항목 일괄 열기, 프로젝트 검색, 메뉴 막대 빠른 접근, 작업 환경 자동 캡처, 외부 앱 상태 복원, 여러 기기 동기화, 다른 사용자와 공유, 저장 공간 최적화, 정교한 Undo, 공개 배포와 자동 업데이트.

### 첫 버전 제외

- 실제 파일 이동·복사·이름 변경·삭제·내용 편집
- 파일 내용 또는 연결된 폴더 내부 목록의 과거 버전 보존
- Git 커밋·브랜치 실행 또는 변경, Git 상태 상시 조회
- 다른 앱의 열린 문서·탭·창 위치 자동 수집·복원
- 화면 상시 녹화, 앱 내 화면 캡처, Accessibility 권한
- 전체 디스크 인덱싱, 연결 폴더의 재귀 탐색·상시 감시
- 서버, 계정, 로그인, 분석 이벤트 전송, 클라우드 동기화
- 자유 캔버스의 좌표 배치, 협업, 브랜치·병합 UI
- 프로젝트와 이력의 영구 삭제·자동 이력 정리

## 5. 핵심 개념과 데이터 규칙

| 개념 | 의미 |
| --- | --- |
| Project | 앱 안에서만 존재하는 논리적 작업 단위. 실제 디렉토리를 생성하지 않는다. |
| Group | 중첩 항목을 담는 가상 그룹. 실제 경로가 없다. |
| Node | 그룹·연결 파일·연결 폴더·웹 링크의 공통 논리 항목. 안정적인 UUID를 가진다. |
| ResourceReference | 특정 실제 파일·폴더에 대한 접근 정보. 대상 교체 시 새 참조를 만든다. |
| Revision | 특정 시점의 프로젝트 이름과 전체 Node 구성을 담는 불변 기록 |
| Checkpoint | 하나의 Revision에 연결된 이름·진행 메모·다음 할 일·이미지 |
| Current | 현재 revision이 가리키는 편집 가능한 구성 |

### 불변식

1. Node의 이름·부모·순서·연결 대상이 바뀌어도 Node UUID는 유지한다.
2. 같은 이름 또는 같은 경로라는 이유로 서로 다른 Node를 병합하지 않는다.
3. ResourceReference의 실제 대상 교체는 새 reference ID를 만든다. 기존 revision의 대상은 바뀌지 않는다.
4. Revision은 수정하지 않는다. 복원도 새로운 revision을 추가한다.
5. 현재 구성과 그에 대응하는 revision은 함께 저장되거나 함께 실패한다.
6. 과거 구성은 현재의 수정 가능한 Node 객체를 공유하지 않는다.
7. 과거 표시 이름·그룹·순서·참조 대상·기록 당시 경로는 현재 변경에 영향을 받지 않는다.
8. 권한·북마크 갱신과 실제 파일 접근 상태는 구성 이력과 분리한다.
9. 실제 파일이 삭제되거나 볼륨이 분리되어도 논리적 항목과 이력은 유지한다.
10. 같은 실제 대상을 여러 그룹·프로젝트에 연결할 수 있다. 하나의 Node는 부모 하나만 가진다.
11. 트리에는 순환이 없다. 자신이나 자손 안으로 그룹을 이동할 수 없다.
12. 과거 시점에서 대상이 실제 존재했는지와 현재 존재하는지를 혼동하지 않는다. 첫 버전은 당시 접근 상태를 증명하지 않는다.

같은 부모 아래 동일한 표시 이름을 허용한다. 항목 종류와 실제 경로를 상세 화면에서 구분한다. 빈 이름은 허용하지 않고 앞뒤 공백을 정리한다.

연결 폴더는 가상 그룹과 구분한다. 앱의 트리에서는 연결 폴더를 하위 가상 항목의 부모로 사용하지 않는다. 내부 파일 탐색은 Finder 등 외부 앱에서 한다. 파일·폴더 종류 전환은 첫 버전에서 새 항목 생성으로 처리한다.

## 6. 화면과 주요 흐름

### 기본 창

- 왼쪽: 프로젝트 목록, 새 프로젝트, 보관된 프로젝트 접근
- 중앙: 선택 프로젝트의 현재 구성 또는 과거 구성 트리
- 상세 영역: 선택 항목의 표시 이름·연결 대상·상태 또는 체크포인트의 메모
- 프로젝트 수준에서 현재 구성·이력·체크포인트에 접근
- 이력 모드에는 기록 시각과 '과거 구성 · 읽기 전용'을 명확하게 표시
- 앱을 다시 열면 마지막 프로젝트로 돌아가되, 기본 진입은 현재 구성으로 한다.

처음 실행할 때는 빈 프로젝트 목록과 '프로젝트 만들기' 동작을 제공한다. 샘플 자료나 전체 디스크 접근을 강제하지 않는다. 시스템 테마와 기본 접근성을 따르고, 중요한 상태를 색상만으로 전달하지 않는다. 기능은 메뉴·버튼·키보드로 접근 가능해야 한다.

### A. 프로젝트와 연결 만들기

1. 프로젝트 이름을 입력해 생성한다. 빈 초기 구성의 첫 revision을 기록한다.
2. 가상 그룹을 만든다.
3. 파일 선택 또는 Finder 드래그로 실제 파일·폴더를 연결한다.
4. 초기 표시 이름은 대상 이름을 사용하고 자유롭게 변경할 수 있다.
5. 웹 링크는 이름과 HTTP/HTTPS URL로 추가한다. 첫 버전은 웹 링크 프리뷰를 가져오지 않는다.
6. 여러 파일을 한 번에 추가하면 단일 사용자 작업으로 revision 하나를 남긴다.

선택 취소, 같은 값으로 확정, 유효하지 않은 입력은 revision을 만들지 않는다. 여러 항목 중 일부의 북마크 생성에 실패하면 전체 추가를 취소하고 재시도할 수 있도록 한다.

### B. backend 대상 교체

1. `backend` 연결 폴더의 '연결 대상 변경'을 선택한다.
2. 다른 실제 폴더를 선택한다.
3. 기존·새 경로를 보여 주고 변경을 확정한다.
4. 이름·Node ID·부모·순서는 유지하고 대상 교체 revision 하나를 기록한다.
5. 현재 구성에서는 새 대상을 열고, 과거 구성에서는 당시 대상을 연다.

선택 취소 또는 같은 실제 대상을 재선택한 경우 의미 없는 교체 revision을 만들지 않는다. 경로 문자열만으로 동일 대상 여부를 확정하지 않는다. 동일성 판정이 불가능하면 사용자에게 대상 교체로 기록될 것을 알린다.

### C. 배치와 제거

가상 그룹 안으로 이동하거나 형제 순서를 바꿀 수 있다. 앱 내부 드래그는 논리적 배치만 바꾼다. 외부 파일을 가상 그룹에 드롭하면 연결을 추가한다. 연결 폴더 위로 드롭하는 것은 원본 폴더에 파일을 옮기는 동작이 아니며, 첫 버전에서는 해당 드롭을 거부한다.

'연결 제거'는 현재 구성에서 Node를 제거한다. 그룹 제거 시 포함된 가상 항목 수를 보여 주고 함께 제거할지 확인한다. 과거 revision은 유지하고 디스크 대상은 삭제하지 않는다. 화면 문구에 '파일 삭제'를 사용하지 않는다.

보관된 프로젝트는 편집을 막고 조회·내보내기·새 프로젝트 생성은 허용한다. 보관 상태는 프로젝트 목록 관리 정보이며 구성 revision을 만들지 않는다. 편집은 보관 해제 후 가능하다.

### D. 과거 구성 확인

1. 이력에서 revision을 선택하거나 원하는 날짜·시간을 지정한다.
2. 선택 시점 이하의 기록 중 마지막 구성을 표시한다.
3. 실제 revision 기록 시각을 함께 표시한다. 매일 스냅샷이 존재하는 것처럼 표현하지 않는다.
4. 프로젝트 생성 이전의 시점은 '이 시점의 기록 없음'으로 표시한다.
5. 시간을 거슬러 조회해도 현재 구성은 변경하지 않는다.

저장 시각은 절대 시각으로 저장하고 표시·날짜 선택은 사용자 시스템 시간대를 따른다. revision 순번으로 기록 순서를 보장한다. 시계가 뒤로 이동한 경우 날짜 조회는 기록 시각 이하에서 가장 늦은 시각을 선택하고, 같은 시각은 순번으로 결정한다. 목록의 작업 순서는 순번이 기준이다.

과거의 파일·폴더를 열 때는 해당 reference가 현재 해석하는 대상을 연다. '당시 경로'와 경로가 달라졌다면 '현재 위치'를 구분해서 표시한다. 실제 파일 내용은 현재 내용이라는 설명을 이력 화면에 제공한다.

### E. 차이 비교

같은 프로젝트의 두 revision을 비교할 수 있다. 과거 revision과 현재 구성 비교를 기본 빠른 동작으로 제공한다.

- 추가, 제거, 표시 이름 변경, 그룹 이동, 순서 변경, 대상 교체를 구분
- 하나의 Node에 여러 변화가 있으면 함께 표시
- 변경 전·후 표시 이름·그룹 위치·대상 경로를 제공
- 프로젝트 이름 변경도 비교에 표시
- 변화가 없으면 명확한 빈 상태 표시
- 그룹 이동 시 하위 Node의 직접 부모가 바뀌지 않았다면 모든 자손을 개별 이동으로 중복 계산하지 않음
- 앞쪽 항목 삽입으로 정렬 인덱스만 밀린 경우를 모든 형제의 재정렬로 표현하지 않음

비교는 저장된 구성 정보만 사용한다. 파일 시스템이나 네트워크가 끊겨도 수행할 수 있어야 한다.

### F. 복원과 새 프로젝트 만들기

과거 구성의 '이 구성으로 복원'은 현재와의 차이를 먼저 보여 준다. 사용자가 확정하면 현재의 프로젝트 이름과 Node 구성을 해당 시점으로 바꾸고, 출처 revision ID가 있는 새 revision을 생성한다. 기존 기록과 체크포인트는 유지한다. 복원 대상과 현재 구성이 동일하면 새로운 revision을 만들지 않는다.

복원 후 연결 대상이 없거나 권한이 부족해도 기록된 구성 자체는 복원한다. 접근 불가능한 항목을 제외해서 조용히 다른 구성으로 바꾸지 않는다. 누락 상태와 해결 동작을 표시한다.

'이 구성에서 새 프로젝트 만들기'는 사용자가 입력한 새 프로젝트 이름과 선택 구성의 복사본으로 시작한다. 프로젝트·Node에 새 UUID를 부여하고 기존 부모 관계를 재매핑한다. 연결 참조는 같은 로컬 대상과 접근 정보를 사용할 수 있다. 원본 프로젝트와 revision의 출처 정보를 기록하고, 원본 이력·체크포인트 전체는 복사하지 않는다. 새 프로젝트의 첫 revision은 복사된 구성이다.

### G. 체크포인트 남기기와 재개

현재 저장된 구성에서 '체크포인트 저장'을 선택한다. 제목은 필수이고 진행 메모·다음 할 일·이미지는 선택이다. 파일·폴더 선택과 별개인 앱 내부 문맥을 기록한다. 웹 링크는 구성의 Node로 관리하고 체크포인트는 해당 revision을 통해 링크 구성을 참조한다.

작성 시작 시 연결할 revision을 고정하고, 저장 전까지 구성 편집을 막는 시트로 구현한다. 제목·메모 입력마다 구성 revision을 만들지 않는다. 구성 변경이 없으면 기존 revision에 체크포인트를 붙인다. 사용자의 선택·그룹 펼침 상태·창 위치는 구성 revision의 대상이 아니다.

저장된 체크포인트는 첫 버전에서 불변이다. 수정이 필요하면 같은 revision에 새 체크포인트를 저장한다. 여러 체크포인트가 같은 revision을 참조할 수 있다. 체크포인트 조회는 연결된 과거 구성을 읽기 전용으로 보여 주며, 현재로 복원하는 동작은 별도로 수행한다.

이미지는 이미 찍은 PNG/JPEG 파일을 선택한다. 파일 내용을 앱 저장소로 복사해 원본 이미지가 이동·삭제되어도 첨부를 유지한다. 사용자 자료 원본을 복제하지 않는 원칙에서 명시적으로 선택한 첨부 이미지만 예외다. 이미지·메모 저장 실패 시 체크포인트를 부분 생성하지 않는다. 미완성 입력은 실패 후에도 재시도할 수 있게 유지한다.

### H. 연결 오류와 재연결

정상, 권한 필요, 대상 없음, 볼륨 연결 필요, 확인 실패를 가능한 범위에서 구분한다. 판정 근거가 부족하면 '확인 실패'로 표시하고 존재 여부를 단정하지 않는다.

오류 항목은 트리에 남겨 두고 '다시 선택', '상태 새로고침'을 제공한다. 현재 reference의 같은 대상에 대한 권한 복구나 stale bookmark 갱신은 구성 revision을 만들지 않는다. 다른 대상으로 교체하면 새 reference와 revision을 만든다.

과거 화면에서 재연결은 같은 대상의 접근 복구만 허용한다. 과거 항목을 다른 대상에 덮어쓰지 않는다. 다른 대상을 사용하려면 현재 구성으로 돌아가 교체하거나 과거 구성에서 새 프로젝트를 만든다.

### I. 내보내기·가져오기

프로젝트 하나의 현재 구성, 전체 revision, 체크포인트, 이미지 첨부, schema version을 내보낸다. 기록된 경로가 포함된다는 안내를 제공한다. 실제 연결 대상 파일 내용은 내보내지 않는다.

첫 버전 내보내기 형식은 사용자 선택 위치의 폴더 묶음이다. `manifest.json`과 `attachments/`를 사용하고 ZIP 의존성은 추가하지 않는다. sandbox의 내보내기 위치 접근은 저장/위치 선택 절차에서 별도로 얻는다. 이는 연결 대상 원본의 read-only 정책과 다른 권한이다.

가져오기는 기존 프로젝트 덮어쓰기 대신 새 프로젝트로 생성한다. Project·Node·Revision·Checkpoint·ResourceReference ID를 재매핑하면서 내부 관계와 Node의 이력상 동일성을 유지한다. 원본 ID는 필요 시 provenance로만 보존한다. 현재 구성 포인터와 모든 첨부 관계를 검증한다. 이식 불가능한 북마크 권한에 의존하지 않고 필요한 로컬 대상을 다시 선택하도록 한다.

손상된 구성, 지원하지 않는 schema version, 누락된 필수 첨부, 잘못된 트리 관계는 가져오기 전에 검증하여 전체 가져오기를 중단한다. 경로가 없는 실제 자료는 데이터 손상이 아니므로 구성 가져오기는 가능하며 재연결 대상으로 표시한다. 첨부 경로가 가져오기 폴더 밖을 가리키면 거부한다. 기존 프로젝트와 원본 자료를 부분 변경하지 않는다.

## 7. 기록 정책과 저장 안정성

- 초기 빈 구성과 확정된 변경마다 전체 메타데이터 스냅샷을 기록한다.
- 프로젝트 이름, Node 추가·제거·이름·부모·순서·대상·웹 URL 변경이 기록 대상이다.
- 여러 파일 추가, 그룹과 자손 제거, 한 번의 드롭은 각각 revision 하나다.
- 입력 중간 상태, 취소, 무변경 확정, 조회, 대상 열기, 접근 상태 갱신은 기록하지 않는다.
- 네트워크, 외부 앱, 파일 접근 실패는 이미 저장된 이력을 변경하지 않는다.
- 현재 구성 저장과 revision 저장 실패 시 이전의 성공한 구성으로 되돌린다.
- 저장 완료 표시는 실제 저장 성공 후에만 제공한다.
- 인접한 요청을 직렬화해 중복 순번·누락·저장 경쟁을 막는다.
- 같은 DB 작업으로 처리할 수 없는 첨부 파일 저장은 staging과 실패 정리로 부분 상태를 방지한다.
- 첫 버전은 이력을 임의로 압축·정리·삭제하지 않는다.
- 데이터 저장소를 열 수 없으면 오류와 복구 선택지를 제공하고 새 빈 DB로 조용히 교체하지 않는다.

## 8. 비기능 요구와 기술 기준

세부 기술 선택은 [TECH_STACK.md](./TECH_STACK.md)를 따른다. Swift 6 language mode, SwiftUI, 필요한 AppKit 연동, Observation, SwiftData, Codable, App Sandbox와 app-scoped bookmarks가 기본이다. 최소 macOS 15, 초기 arm64, 외부 패키지 0개로 시작한다.

### 경량화

전체 디스크 인덱싱·연결 폴더 재귀 스캔·상시 화면 기록을 하지 않는다. 연결 상태는 선택·열기·명시적 새로고침 시 확인한다. 이력 목록은 필요한 양만 로드하고, 선택된 revision만 디코딩한다. 파일 I/O·이미지 처리로 주 UI를 막지 않는다.

검증 데이터는 프로젝트 10개, 선택 프로젝트 Node 500개(가상 그룹 50개 포함), 선택 프로젝트 revision 1,000개를 기준으로 마련한다. 이는 성능 검증용 규모이며 사용자 수나 기능 제한이 아니다.

Release 빌드에서 시작 시간, 유휴 CPU·메모리, revision 저장 지연, 과거 구성 표시 시간, 비교 시간, DB·첨부 크기를 기록한다. 최초 기준 측정 후 정량 목표를 정한다. 측정 전 임의의 메모리 수치를 약속하지 않는다. 대량 기록 로딩으로 앱이 응답하지 않거나 모든 revision을 항상 디코딩하는 구현은 수용하지 않는다.

### 로컬성과 접근성

로그인 없이 오프라인에서 핵심 기능을 사용한다. 웹 링크 열기는 해당 사이트와 기본 브라우저의 동작이다. 앱 자체가 링크 내용을 수집하거나 사용자 자료를 외부로 전송하지 않는다.

파일·폴더 접근은 사용자 선택 범위에 한정한다. 로그에 메모 원문·이미지 내용·전체 구성 JSON을 남기지 않는다. 화면에서 주요 동작에 접근성 레이블·키보드 접근·선택 상태를 제공한다. 과거/현재 및 오류 상태를 색상만으로 구분하지 않는다.

### UI 언어와 전달

첫 버전 기본 UI는 한국어로 작성하고 문자열을 분리해 이후 현지화할 수 있게 한다. 용어는 연결 제거, 연결 대상 변경, 과거 구성, 구성 복원, 체크포인트로 통일한다. 사용자에게 DB·JSON·bookmark blob 같은 구현 용어를 노출하지 않는다.

## 10. 구현 순서와 인계 지침

### 단계 1: 데이터와 파일 접근 기반

네이티브 앱 프로젝트·sandbox 설정, 데이터 스키마 V1, 불변 snapshot 타입, 구성 변경 서비스, 파일 선택·북마크 생성·재실행 후 접근을 먼저 구현한다. 최소 트리에서 이름 유지와 대상 교체를 검증한다.

### 단계 2: 구성 관리

프로젝트·가상 그룹·연결·웹 링크 CRUD, 트리 배치, 원본 열기, 오류 상태를 완성한다. 저장 실패와 순환 방지를 검증한다.

### 단계 3: 이력

자동 revision, 날짜 조회, 차이 비교, 복원·복제를 완성한다. 변경·재실행·복원 뒤에도 과거 구성이 유지되는 것을 확인한다.

### 단계 4: 작업 맥락과 데이터 이동

체크포인트, 메모·다음 할 일, 선택 이미지 첨부, 내보내기·가져오기를 완성한다.

### 단계 5: 실제 개인 사용 검증

Release 앱으로 대표 시나리오와 A01~A18을 검증한다. Instruments 측정, 파일 이동·볼륨 분리, 접근 복구, UI 키보드 접근, 최소 OS 호환성 확인 결과를 보고한다.

### 구현 에이전트가 지킬 기준

- 이 문서는 제품 동작, TECH_STACK.md는 기술 선택의 기준이다. 서로 모순되면 조용히 선택하지 않고 모순을 기록한다.
- 이 PRD의 구체화 선택은 구현을 위한 기본값이다: 트리 배치, 한국어 UI, 불변 체크포인트, 프로젝트 보관, 폴더 형태 export, 새 프로젝트로 import.
- 단순히 다른 에이전트에게 인계된다는 이유로 새 채팅을 생성하거나 사용자에게 반복 확인하지 않는다.
- 핵심 데이터 의미나 납품 범위를 바꾸는 경우 이유·대안·영향을 설명하고 사용자와 합의한다.
- 코드 구조·기본 레이아웃·표준 API 사용은 이 문서 안에서 자율적으로 결정한다.
- 데이터 이력은 SwiftData가 자동 제공한다고 가정하지 않는다. 실제 앱의 불변식과 저장 정책을 구현한다.
- 파일 내용 버전 관리, 화면 상시 기록, 외부 앱 복원으로 범위를 확대하지 않는다.
- 빌드 성공과 실제 sandbox 접근 검증을 구분한다. macOS 15 검증을 못 했으면 미검증으로 보고한다.
- 결과물은 앱 소스·표준 Xcode 프로젝트·실행 방법·검증 결과다. 프로토타입 화면만으로 완료 처리하지 않는다.
- 학습용 설명은 실제 구현을 이해하는 데 필요한 수준으로 제공한다.
